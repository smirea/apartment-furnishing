# Environment

- **One schema, generated outputs.** The root `.env` declares every setting with its type and default. The root `.env.local` holds this checkout's values. `bun run env:generate` (`env-manager gen --local`) writes the git-ignored values files and the tracked `env.ts` readers. Never edit a generated file by hand.
- **Readers are committed exactly as generated.** oxfmt and oxlint ignore them, so regenerating in a worktree or in CI never dirties the tree.
- **Local mode until values need to be shared.** `# env-manager local:true` in `.env` keeps env-manager offline and stops it from committing on its own. To move values into AWS Secrets Manager, run `env-manager set local false`, then `env-manager env set dev` and `env-manager up`. `env set` downloads an environment that exists; one that doesn't yet keeps the current `.env.local` and is seeded by the next `up`. For `prod`, run `env-manager env set prod`, put the production values in `.env.local` with `APP_ENV=production`, and run `env-manager up`. `.env.local` records which environment its values came from, and `up` refuses values pulled for a different one, so dev values can't land in prod. Switch environments with `env-manager env set <env>`, re-pull with `env-manager down`. Use the global `env-manager` for these: it loads the AWS credentials from its own checkout, which the pinned copy in `node_modules` cannot see.
- **Agents and CI never need AWS.** They run `env-manager gen --local`, which uses the schema defaults, so every default must be harmless and enough to start the app and run the tests.
- **Secrets are optional in the schema and required in `config.ts`.** That keeps offline generation working. `apps/server/src/config.ts` lists the settings production needs in `REQUIRED_IN_PRODUCTION`, and the server refuses to start without them instead of failing on the first request that reads one.
- **`APP_ENV`** is `development` by default and `production` in `prod`.
